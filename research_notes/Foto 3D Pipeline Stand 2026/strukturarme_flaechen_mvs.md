# Dense multi-view reconstruction of textureless facades (white plaster) - freely usable code, state 2024-2026

Research date: 2026-11-19. Licenses were read directly from the repositories' LICENSE files / GitHub API / Hugging Face model-card tags on that day (not from secondary sources) unless stated otherwise. "8 GB" = RTX 4060 8 GB VRAM, 15 GB RAM. Where a statement is my own reasoning and not in a source it is under "Inferences"; where nothing reliable was found it is under "Gaps".

## 1. PatchMatch variants with planar / deformable-patch priors (ACMM, ACMP, ACMMP, APD-MVS, HPM-MVS, MP-MVS, SD-MVS, DVP-MVS and newer)

### Takeaway
The only variants that are both published with code AND carry a permissive license are ACMM / ACMP / ACMMP (MIT), APD-MVS (MIT) and DVP-MVS (MIT code, but needs Depth Anything V2 weights whose size/licence is not stated). On ETH3D, completeness at 2 cm rises from about 63 % (COLMAP) to 74-76 % (ACMM/ACMP), 81 % (ACMMP), 86 % (APD-MVS) and 89 % (DVP-MVS, HPM-MVS++) - this is the best-documented gain for textureless areas of all options in this report. HPM-MVS, HPM-MVS++, MP-MVS, SD-MVS, MSP-MVS and SED-MVS have public code but NO license file (legally: all rights reserved).

### Inferences
- Demonstrated (benchmarks): relative to COLMAP, ACMP/ACMM add roughly 11-13 points of completeness on ETH3D at equal accuracy (~90.5 %), ACMMP about 18 points, APD-MVS about 23 points, DVP-MVS about 26 points. ETH3D contains many textureless indoor walls, so this is the closest published proxy for white plaster. Not demonstrated: any of these on internet photo collections with mixed cameras/lighting - ETH3D and TnT are single-camera, single-session captures. The NCC cost in all of them is illumination-normalised per patch, but large exposure/season differences will still reduce the planar-prior support. The gain on a textured outdoor facade is small (ETH3D "facade": 74.2 -> 76.6).
- Planar priors help exactly where the wall really is planar. For plaster walls that is the right bias; for reliefs, cornices, rustication it can flatten detail (ACMP paper itself calls its planar models "biased, especially for non-planar regions"). This fits the project rule that the cloud is only a position veto/height check, not the source of shape.
- Practical choice for commercial use: APD-MVS (MIT, no network weights, highest completeness among clean-license options) and ACMMP (MIT, oldest/most used). DVP-MVS is MIT but only usable commercially if it runs with the Depth-Anything-V2-Small (Apache) weights; the README does not say which size it expects.
- Code with no license file (HPM-MVS, HPM-MVS++, MP-MVS, SD-MVS, MSP-MVS, SED-MVS) grants no usage rights by default; commercial use would need written permission from the authors. SD-MVS/MSP-MVS/SED-MVS additionally depend on SAM-family models (own licenses).
- 8 GB: HPM-MVS / HPM-MVS++ are stated as tested on an 8 GB RTX 3070, so that family demonstrably runs on 8 GB. ACMMP was tested on 11 GB, APD/DVP on 24 GB; these are per-image GPU PatchMatch codes whose memory scales with image size and number of source views, so 1600 px (the current COLMAP setting) is plausible on 8 GB, full-resolution phone images are not guaranteed. Unknown until tried.
- Effort: low to medium. All read a COLMAP sparse model through a converter script to MVSNet-style `cams/` + `images/` + `pair.txt`; build is plain CMake + CUDA (edit `-gencode arch=compute_89` for the RTX 4060 - Ada generation is compute capability 8.9). Images must be undistorted first (COLMAP `image_undistorter`). Fusion is built in, output is a .ply. Expect half a day to a day per method including build fixes on a modern CUDA/OpenCV.

### Gaps
- No published VRAM figures for ACMMP, APD-MVS, DVP-MVS at a given resolution were found (DVP-MVS has them only as a figure).
- Which Depth Anything V2 model size DVP-MVS uses is not stated in README or paper text read; must be checked in the code before commercial use.
- APDe-MVS: existence announced by the APD-MVS README, but license and content could not be read (404 on main).
- No benchmark of any of these methods on internet photo collections (e.g. IMC/PhotoTourism-style data) was found.
- COLMAP is not listed in the part of the current ETH3D leaderboard that could be read (page truncated); COLMAP numbers above come from the ACMP paper quoting Schöps et al.

## 2. COLMAP's own settings that matter for textureless areas

### Takeaway
The official FAQ gives exactly three levers for weakly textured surfaces - higher `max_image_size`, larger `window_radius`, lower `filter_min_ncc` - without numbers, and says `StereoFusion.min_num_pixels` trades outliers against completeness. No measurements of how much these help on white walls were found; papers uniformly treat COLMAP's photometric-only cost with a fixed window as the root cause, which parameter tuning cannot remove.

### Cited Findings
- FAQ, "Improving dense reconstruction results for weakly textured surfaces": "For scenes with weakly textured surfaces it can help to have a high resolution of the input images (`--PatchMatchStereo.max_image_size`) and a large patch window radius (`--PatchMatchStereo.window_radius`)"; additionally reduce `--PatchMatchStereo.filter_min_ncc` to lower the filtering threshold for the photometric consistency cost. No values given — [COLMAP FAQ](https://colmap.github.io/faq.html)
- FAQ, speed-up section: `--PatchMatchStereo.geom_consistency false` (then enable `--PatchMatchStereo.filter true`), `window_step 2`, lower `window_radius`, `num_iterations`, `num_samples`, lower `max_image_size`; the FAQ warns these "might degrade the quality of the dense reconstruction results" — [COLMAP FAQ](https://colmap.github.io/faq.html)
- FAQ, memory: on GPU out-of-memory lower `max_image_size` or reduce the number of source images in `stereo/patch-match.cfg` (e.g. `__auto__, 30` -> `__auto__, 10`); enabling `geom_consistency` increases GPU memory needs; `cache_size` options control CPU RAM (in GB) — [COLMAP FAQ](https://colmap.github.io/faq.html)
- FAQ, fusion: if the fused cloud has too many outliers increase `--StereoFusion.min_num_pixels`; for reconstructions from known poses the FAQ recommends `--StereoFusion.min_num_pixels 1` (points may otherwise fail to fuse). `max_reproj_error`, `max_depth_error`, `max_normal_error` are not discussed in the FAQ — [COLMAP FAQ](https://colmap.github.io/faq.html)
- Source defaults (from a mirror of `patch_match.h`, not the official repo): `window_radius = 5` (documented as "Half window size to compute NCC photo-consistency cost"), `filter_min_ncc = 0.1` ("minimum NCC coefficient for pixel to be photo-consistent"), `filter_min_triangulation_angle = 3.0` degrees — [patch_match.h mirror](https://huggingface.co/camenduru/ceres-solver-v1/blob/main/colmap/src/mvs/patch_match.h)
- One paper (found via search summary, not read in full) changed `filter_min_num_consistent` from its default 2 to 1 — [search result set incl. arXiv 2309.13294 / 2311.07600](https://arxiv.org/pdf/2311.07600)
- COLMAP's limitation as stated by follow-up work: the photometric measure is central so "untextured regions are not managed well"; TAPA-MVS addresses it by assuming such regions are piecewise flat — [TAPA-MVS, ICCV 2019](https://openaccess.thecvf.com/content_ICCV_2019/papers/Romanoni_TAPA-MVS_Textureless-Aware_PAtchMatch_Multi-View_Stereo_ICCV_2019_paper.pdf)
- Measured effect of COLMAP's fusion being strict: on ETH3D COLMAP reaches ~92 % accuracy at ~63 % completeness, whereas OpenMVS "employs a different fusion scheme with a relaxed number of consistent views for a pixel, which leads to noisy point clouds with low accuracy and high completeness" (82 % / 78.5 %) — [ACMP paper](https://arxiv.org/abs/1912.11744)
- COLMAP license: new BSD (3-clause); the LICENSE notes that dependencies are licensed separately and "Building COLMAP with these dependencies may affect the resulting COLMAP license" — [colmap/colmap LICENSE](https://github.com/colmap/colmap/blob/main/LICENSE)

### Inferences
- What the settings do for a white wall (reasoning from the algorithm, not measured): (a) `window_radius` 5 -> 9..11 with `window_step 2` enlarges the NCC support so that faint plaster structure/shading gradients enter the patch; cost grows with the window area, `window_step 2` halves the sampling per axis and keeps it affordable. (b) `filter_min_ncc` 0.1 -> 0.05 or lower keeps weak-but-consistent matches; only safe together with `geom_consistency true` and `filter_min_num_consistent >= 2`, otherwise noise. (c) `max_image_size` 1600 -> 2400..3200 makes plaster grain visible; on 8 GB this is the setting most likely to hit memory limits, reduce source images per reference to compensate. (d) Fusion: `min_num_pixels` (default 5 in COLMAP, value from memory - verify in `colmap stereo_fusion -h`) down to 3 or 2 directly increases completeness where only few views agree; `max_reproj_error` (default 2 px) and `max_depth_error` (default 0.01 relative) decide whether noisy wall depths of different views are accepted as the same point - relaxing them fills walls at the price of thickness/noise. These defaults are from memory and must be confirmed on the installed version.
- Expected gain: modest. The FAQ's own phrasing is "it can help". Published evidence says the structural fixes (multi-scale, planar prior, deformable patch: section 1) give +11 to +26 points of completeness, which parameter tuning cannot reach. But the effort is near zero (one A/B run on an existing workspace), so it is the first thing to try.
- Since project rules use the cloud only as position veto, relaxed fusion thresholds on wall regions are acceptable in a second, separately stored "fill" cloud rather than replacing the strict cloud.

### Gaps
- No COLMAP GitHub issue with measured before/after numbers for white walls could be retrieved (search returned no issue threads); the report writer should not claim documented community guidance beyond the FAQ.
- No source found for the exact current defaults of the StereoFusion options; the values quoted in Inferences are unverified.
- No published ablation of `window_radius` / `filter_min_ncc` on ETH3D for COLMAP was found.

## 3. OpenMVS (DensifyPointCloud) versus COLMAP PatchMatch on low-texture facades

### Takeaway
Published ETH3D numbers show OpenMVS as markedly more complete than COLMAP (78.5 % vs 63.0 % at 2 cm; outdoor 86.4 % vs 73.0 %) but about 10 points less accurate - the completeness comes from laxer fusion, and at depth-map level OpenMVS was actually worse than COLMAP. License is AGPL-3.0; the GNU position is that program output is not covered by the program's license, so selling point clouds/models is generally considered unaffected, while distributing or network-serving a modified OpenMVS would trigger source-release duties.

### Cited Findings
- License: AGPL-3.0; actively maintained (push on 2026-11-19), 4200 stars — [cdcseacave/openMVS](https://github.com/cdcseacave/openMVS)
- ETH3D test, point clouds, 2 cm: OpenMVS accuracy 81.98 / completeness 78.54 / F1 79.77 versus COLMAP 91.97 / 62.98 / 73.01. Outdoor: OpenMVS 81.93 / 86.41 / 84.09 versus COLMAP 92.04 / 72.98 / 80.81. Indoor: OpenMVS 82.00 / 75.92 / 78.33 versus COLMAP 91.95 / 59.65 / 70.41 — [ACMP paper, Table 2 (values from Schöps et al.)](https://arxiv.org/abs/1912.11744)
- Explanation given by the ACMP authors: OpenMVS "employs a different fusion scheme with a relaxed number of consistent views for a pixel, which leads to noisy point clouds with low accuracy and high completeness" — [ACMP paper](https://arxiv.org/abs/1912.11744)
- Depth-map level (ETH3D training, % pixels with error < 2 cm, average): OpenMVS 55.2 versus COLMAP 65.0; on "facade": OpenMVS 55.4 versus COLMAP 74.2; at 10 cm: 66.5 versus 73.7 — [ACMP paper, Table 1](https://arxiv.org/abs/1912.11744)
- TSAR-MVS paper table shows the same pattern (COLMAP 67.66 F1 vs OpenMVS 76.15 F1 at 2 cm in one ETH3D block; table layout hard to parse, treat as indicative) — [TSAR-MVS, arXiv 2308.09990](https://arxiv.org/pdf/2308.09990)
- GPL-family licenses and output: per the FSF, the output of a program is generally not covered by the copyright on the program's code; output inherits the copyright status of the input, except where the program copies parts of itself into the output — [FSF licensing blog on the GPL FAQ](https://www.fsf.org/blogs/licensing/licensing-and-compliance-lab-the-most-frequently-asked-frequently-asked-questions)

### Inferences
- These numbers are from the 2017-2019 versions of both tools. OpenMVS has since changed its PatchMatch (and has an optional CUDA path); no current head-to-head on low-texture facades was found. Treat "OpenMVS is more complete but noisier" as demonstrated for the old versions and plausible for current ones.
- For white plaster the old evidence is double-edged: OpenMVS fills more, but its raw depth maps were less accurate than COLMAP's, so the fill is partly noise. Similar completeness may be reachable by relaxing COLMAP's own fusion (section 2), without adding an AGPL component.
- AGPL in practice for this project: (1) running unmodified OpenMVS in-house and selling the resulting models/prints: no obligation on the output under the FSF reading (a point cloud contains no OpenMVS code). (2) Shipping OpenMVS binaries to a customer, or offering it as a network service with modifications: source of the (modified) program must be offered under AGPL. (3) Linking OpenMVS libraries into own pipeline code and distributing that code makes the combination AGPL. Calling the executables as separate processes from own scripts is the usual way to keep the own code separate. This is not legal advice; for significant revenue a lawyer should confirm.
- 8 GB: DensifyPointCloud is primarily CPU-based with modest memory at reduced resolution levels, so it is feasible on this machine; the 15 GB RAM limit is the more relevant constraint for large scenes (use `--resolution-level` / sub-scene splitting).
- Effort: low (COLMAP -> OpenMVS import via `InterfaceCOLMAP`); expected gain: medium completeness gain with accuracy loss; unknown on current versions.

### Gaps
- No 2023-2026 benchmark comparing current OpenMVS with current COLMAP on textureless outdoor facades was found.
- A search summary mentioned a study finding that the CPU and GPU PatchMatch implementations in OpenMVS produce different point clouds, but the exact source could not be pinned down; not citable as is.
- The GNU GPL FAQ entry itself (gnu.org, "GPLOutput") was not fetched directly; the FSF blog post summarising it was the source.

## 4. Learned MVS (MVSFormer++, GeoMVSNet, MVSAnywhere, feed-forward 3D models)

### Takeaway
MVSAnywhere is the learned MVS that is demonstrated to generalise zero-shot (best average on the Robust MVD benchmark incl. ETH3D and Tanks and Temples) and it reads COLMAP data - but its license is explicitly NON-COMMERCIAL (Niantic). MVSFormer++ and GeoMVSNet are Apache-2.0 code but were trained on DTU/BlendedMVS and are not shown to work on internet photos. The commercially clean learned options today are the Apache-licensed checkpoints of MapAnything (`facebook/map-anything-apache`) and Depth Anything 3 (Small/Base, Metric-Large, Mono-Large); VGGT has a separate gated "Commercial" checkpoint.

### Cited Findings
- MVSAnywhere (CVPR 2025): LICENSE header: "This Software is licensed under the terms of the following MVSAnywhere license which allows for non-commercial use only. For any other use ... contact partnerships@nianticlabs.com"; "Copyright Niantic, Inc. 2025. Patent Pending." README: "This code is for non-commercial use" — [nianticlabs/mvsanywhere LICENSE](https://github.com/nianticlabs/mvsanywhere/blob/main/LICENSE)
- MVSAnywhere method: plane-sweep cost volume + transformer, monocular ViT-Base branch initialised from Depth Anything V2 (Base) relative-depth weights, cost-volume ViT from DINOv2; needs posed images with intrinsics; variable number of source views; trained and run at 640 x 480 on eight synthetic datasets (Hypersim, TartanAir, BlendedMVG, MatrixCity, VKITTI2, Dynamic Replica, MVSSynth, SAIL-VOS 3D) — [MVSAnywhere paper, arXiv 2503.22430](https://arxiv.org/html/2503.22430v1)
- MVSAnywhere zero-shot results (Robust MVD benchmark; rel error % / inlier ratio tau): average 2.7 / 77.0 versus MVSFormer++ 3.6 / 69.8 and MASt3R with triangulation 3.4 / 70.1; Depth Pro with median scaling 5.6 / 51.7. ETH3D: MVSA 3.2 / 68.0, MASt3R 3.1 / 72.9, MVSFormer++ 5.3 / 57.5. Tanks and Temples: MVSA 2.1 / 90.5, MVSFormer++ 2.2 / 88.6. Runtime 0.12 s per test case; GPU memory not reported — [MVSAnywhere paper](https://arxiv.org/html/2503.22430v1)
- MVSAnywhere README: documents running on COLMAP reconstructions and nerfstudio data, and a Gaussian-splatting regularisation module (`regsplatfacto`); "If you run out of GPU memory, you can try removing the `--fast_cost_volume` flag" — [nianticlabs/mvsanywhere README](https://github.com/nianticlabs/mvsanywhere)
- MVSFormer++ (ICLR 2024): code Apache-2.0; uses DINOv2-B backbone weights; trained on DTU with 4 x 48 GB A6000, fine-tuned on BlendedMVS before Tanks and Temples; pretrained models on OneDrive (no separate weights license stated); custom data via COLMAP + `colmap2mvsnet.py` — [maybeLx/MVSFormerPlusPlus](https://github.com/maybeLx/MVSFormerPlusPlus)
- GeoMVSNet (CVPR 2023): code Apache-2.0, last push 2026-09 — [doubleZ0108/GeoMVSNet](https://github.com/doubleZ0108/GeoMVSNet)
- Learned MVS on ETH3D point-cloud benchmark stays below the best PatchMatch variants: e.g. EPNet F1 83.72 (completeness 87.84), EPP-MVSNet 83.40, IterMVS-LS 80.06, MVSTER 79.01, PatchMatchNet 73.12, versus APD-MVS 87.44 and DVP-MVS 89.60 — [DVP-MVS paper table](https://arxiv.org/html/2412.11578v3)
- MASt3R: CC BY-NC-SA 4.0 (non-commercial) — [naver/mast3r LICENSE](https://github.com/naver/mast3r/blob/main/LICENSE)
- VGGT: code under a Meta "VGGT License"; since 2025-07-29 commercial use permitted (excluding military) but "only the newly released checkpoint VGGT-1B-Commercial is licensed for commercial usage - the original checkpoint remains non-commercial"; that checkpoint is gated on Hugging Face under a "vggt-aup-license" — [facebookresearch/vggt README](https://github.com/facebookresearch/vggt), [HF facebook/VGGT-1B-Commercial](https://huggingface.co/facebook/VGGT-1B-Commercial)
- MapAnything: code Apache-2.0; two checkpoints: `facebook/map-anything` is CC BY-NC 4.0, `facebook/map-anything-apache` is Apache-2.0 (CLI flag `--apache`); has memory-efficient inference with `minibatch_size=1` "for smallest GPU memory consumption"; accepts optional poses/intrinsics/depth as inputs — [facebookresearch/map-anything README](https://github.com/facebookresearch/map-anything), [HF map-anything-apache](https://huggingface.co/facebook/map-anything-apache)
- Depth Anything 3: code Apache-2.0. Per README table: DA3-SMALL (0.08 B params) and DA3-BASE (0.12 B) Apache-2.0, with relative depth + pose estimation + pose conditioning; DA3METRIC-LARGE and DA3MONO-LARGE (0.35 B) Apache-2.0 (monocular only); DA3-LARGE, DA3-GIANT, DA3NESTED-GIANT-LARGE (and their 1.1 versions) CC BY-NC 4.0. DA3-Streaming handles long video "with less than 12GB GPU memory" — [ByteDance-Seed/Depth-Anything-3 README](https://github.com/ByteDance-Seed/Depth-Anything-3)

### Inferences
- "Generalises to internet photo collections" is demonstrated for none of the classic learned MVS nets (MVSFormer++, GeoMVSNet): their benchmarks are DTU / TnT / ETH3D with fine-tuning on BlendedMVS. MVSAnywhere demonstrates zero-shot transfer across datasets but not specifically internet photos, and outputs 640 x 480 depth - too coarse to be a geometry source, adequate as a wall-filling prior. Its license rules it out for sold results unless Niantic licenses it.
- 8 GB: MVSAnywhere at 640 x 480 with a ViT-Base is plausible on 8 GB (not stated). MVSFormer++ at Tanks-and-Temples resolution (about 2 MP, many views) is unlikely to fit in 8 GB without reducing resolution/view count (not stated; the authors trained on 48 GB cards). DA3-Small/Base and MapAnything with minibatch 1 are plausible on 8 GB for tens of views at ~500 px.
- For this project the role of a pose-conditioned feed-forward model (MapAnything-apache, DA3-Base: both accept known cameras) would be the same as mono depth in section 5: a dense, multi-view-consistent depth prior at low resolution that is aligned to SfM/PatchMatch depth and used only where PatchMatch is empty. MapAnything is already on the project's task list (AUFGABENLISTE 16.11.).
- Expected gain: complete wall coverage at coarse resolution (demonstrated qualitatively by these papers on low-texture scenes); metric accuracy on a flat wall depends on alignment to SfM, not on the network. Effort: medium (Python environments, data conversion from COLMAP), half a day to a day each.

## 5. Monocular depth as prior to fill holes; methods that fuse mono depth with SfM/MVS

### Takeaway
Commercially usable mono-depth weights exist: Depth Anything V2 Small (Apache-2.0), Depth Anything 3 Small/Base/Metric-Large/Mono-Large (Apache-2.0), MoGe / MoGe-2 / MoGe-3 (MIT code and MIT-tagged weights), Marigold (Apache code, OpenRAIL++ weights), Metric3D v2 (BSD-2 code, weights license unclear). Not usable commercially: Depth Anything V2 Base/Large/Giant (CC BY-NC), Depth Pro weights (Apple research-only model license), UniDepth (CC BY-NC). - DVP-MVS: uses Depth Anything V2 depth edges and visibility priors inside APD-style PatchMatch (section 1): ETH3D completeness 89.41 versus APD-MVS 85.93 — [DVP-MVS paper](https://arxiv.org/html/2412.11578v3)
- MVSAnywhere: mono ViT features inside a cost volume (section 4; non-commercial) — [MVSAnywhere paper](https://arxiv.org/html/2503.22430v1)

- 2DGS-family findings: monocular depth and normal priors are used to make Gaussian surface reconstruction robust (DN-Splatter added depth and normal supervision to 2DGS); one paper notes 2DGS is sensitive to depth errors because depth mispredictions directly shift the surfels — [DN-Splatter supplemental, WACV 2025](https://openaccess.thecvf.com/content/WACV2025/supplemental/Turkulainen_DN-Splatter_Depth_and_WACV_2025_supplemental.pdf), [2DGS-R, arXiv 2510.16837](https://arxiv.org/pdf/2510.16837)

### Inferences
- The simplest clean-license recipe (plausible, each ingredient is standard but the combination is not benchmarked on facades): per image, predict relative/affine-invariant depth with DA3Mono-Large or MoGe-2 (or DAv2-Small), fit scale + shift (RANSAC, in disparity or depth space depending on the model) against COLMAP's own valid PatchMatch depths and projected SfM points, and use the aligned depth only in pixels where PatchMatch is empty; then run the normal multi-view geometric consistency / fusion on the union so that a filled pixel survives only if several views agree. A single global scale-shift per image leaves low-frequency bending of several percent of depth (cf. Depth Pro median-scaled 5.6 % rel error); on a wall 10 m away that is decimetres, so a LOCAL alignment (per wall segment, or the distance-weighted alignment of Prior Depth Anything) is needed. Prior Depth Anything implements exactly this "precise but incomplete + complete but relative" fusion and is Apache-2.0 end to end when run with `vits` coarse model (Depth Anything V2 Small) - but which DAv2 backbone sizes its released checkpoints are derived from (vitb fine-stage = derived from CC BY-NC Base weights?) must be clarified: the HF tag says Apache-2.0, while Depth Anything V2 Base itself is CC BY-NC. Flag as a license question to resolve before commercial use.
- For a planar plaster wall, a mono prior adds little beyond what a plane fit through the wall's SfM points and edge depths gives; its value is where the wall is not planar (bulges, slanted buttresses, reveals) and as a normal/edge prior (MoGe-2 normals, Marigold normals) to decide WHERE a plane hypothesis may be extended. This matches the DVP-MVS design (mono depth used for edges, not for absolute depth).
- Murre is the most complete ready-made "SfM points -> dense depth -> TSDF" pipeline and its license permits commercial projects after a free registration. Risks: diffusion model (SD2-based) at ~700 x 1200 px on 8 GB is plausible only with ensemble 1 and half precision (not stated); trained on indoor synthetic data; `--max_depth 10.0` default hints at indoor tuning; weights licence not separately stated (SD2 base is OpenRAIL++).
- OpenRAIL++-M (Marigold weights) permits commercial use subject to use-based restrictions (general knowledge of the license family; the report writer should phrase it as "commercial use allowed with use restrictions" and link the license text).
- 8 GB feasibility (plausible, not stated by sources): DAv2-Small, DA3-Small/Base, MoGe-2 ViT-S/B/L, Metric3D ViT-Small: yes at ~518-1024 px. DA3 Mono/Metric-Large (0.35 B params): yes. Marigold / Murre (Stable Diffusion U-Net): yes at <= 768 px with fp16 and ensemble 1, slow. Depth Pro (ViT-L multi-scale at 1536 px): borderline, and weights are research-only anyway.
- Effort: mono depth + scale/shift fill into COLMAP depth maps is a 1-2 day tool (read/write COLMAP `.bin` depth maps, GPU inference, per-segment alignment, then standard `stereo_fusion`); Prior Depth Anything or Murre trials about one day each.

### Gaps
- No publication was found that evaluates "mono depth aligned per image + fused with PatchMatch depth" specifically on textureless building facades from internet photos; the closest are Murre (indoor/street) and Prior Depth Anything (depth-completion benchmarks).
- Murre weights: Hugging Face API returned no public model card under `zju3dv/Murre`; where the checkpoint is hosted and under which terms was not verified.
- Metric3D v2 weights: no explicit license statement found; the README's "commercial inquiries" sentence leaves commercial use of the weights unclear.
- Prior Depth Anything: paper abstract does not name SfM points explicitly as a prior type; suitability for very sparse, unevenly distributed SfM points on a blank wall (the actual failure case: few points ON the wall) is untested. GPU memory not stated.
- Marigold-DC weights license (it reuses Marigold checkpoints) was not separately checked.

## 6. Surface reconstruction alternatives: 2DGS, PGSR, GOF, SuGaR, Neuralangelo, NeuS2 - licenses, 8 GB, plain walls

### Takeaway
All the well-known surface-reconstruction research codebases are non-commercial: 2DGS, GOF and SuGaR ship the Inria/MPII Gaussian-Splatting license, PGSR has its own ZJU non-commercial license, Neuralangelo and NeuS2 are under NVIDIA non-commercial source licenses. The genuinely permissive route is gsplat (Apache-2.0), which includes its own 2DGS trainer, plus nerfstudio/sdfstudio (Apache-2.0) and instant-nsr-pl (MIT). No source demonstrates that any Gaussian method reconstructs a blank white wall metrically better than planar-prior MVS; papers that address weak texture add mono depth/normal priors or planar constraints.

### Inferences
- License bottom line for sold results: 2DGS (official), GOF, SuGaR, PGSR, Neuralangelo, NeuS2, Mip-Splatting = NOT usable without a commercial agreement (Inria offers commercial licensing of 3DGS; ZJU and NVIDIA must be asked). Usable: gsplat's own 2DGS/3DGS implementation (Apache-2.0), nerfstudio and sdfstudio (Apache-2.0; note that sdfstudio's Neuralangelo/NeuS re-implementations are independent code, and optional mono-prior inputs such as Omnidata have their own licenses), instant-nsr-pl (MIT).
- Plain walls: photometric optimisation has the same ambiguity on white plaster as PatchMatch - any depth explains a uniform colour. Gaussian/SDF methods fill the wall by regularisation (2DGS normal consistency, PGSR single-view/multi-view planar constraints, SDF eikonal smoothness), so they give a hole-free surface, but its position is constrained only by the textured borders and SfM-point initialisation. This is plausible reasoning; no source quantifies wall accuracy. The PGSR authors' special flag for weakly textured scenes and the trend to add mono depth/normal priors (DN-Splatter, MVSAnywhere regsplatfacto, GS4Buildings) indicate that plain areas are a known weak point without priors.
- Internet photo collections add appearance variation (exposure, season, people) that vanilla 2DGS/PGSR do not model; "in-the-wild" Gaussian variants exist but were outside this pass. Phone video frames from one session are the favourable case.
- 8 GB: gsplat 2DGS with a capped number of Gaussians and images downscaled to ~1600 px typically fits in 8 GB for a single building (plausible, from general experience with 3DGS memory scaling; not stated by a source). Neuralangelo is known to need far more memory and many hours; NeuS2/instant-ngp-class methods fit in 8 GB but are license-blocked anyway.
- Fit to the project method: a 2DGS/TSDF mesh would be another "dense cloud"-type product, i.e. only position veto / height / cross-check under the project's rules, not a source of form. Its realistic benefit is a hole-free depth render per camera for the facade rectification step, and it competes there with the cheaper options (planar-prior MVS, mono-depth fill).
- Effort: gsplat 2DGS trial about half a day to a day (COLMAP input is supported by the example trainers; mesh via TSDF of rendered depths must be scripted). Expected gain on white walls: uncertain; lower priority than sections 1, 2 and 5.

### Gaps
- No published peak-VRAM figures for 2DGS, GOF, PGSR at given resolution were found; "8 GB feasible" is not demonstrated by a source.
- No quantitative comparison of gsplat's 2DGS trainer against the official 2DGS code on geometry (DTU/TnT) was found in this pass.
- No paper was found that measures Gaussian-surface accuracy specifically on textureless planar facades versus ACMMP/APD-MVS.
- GS4Buildings and wild-photo Gaussian variants were not read; their licenses are unknown.

## 7. Cross-cutting: ranking for one RTX 4060 8 GB with commercial use

### Takeaway
Ordered by (documented gain) x (license cleanliness) / effort: first COLMAP parameter A/B (free), then APD-MVS or ACMMP on the existing COLMAP workspace (MIT, biggest benchmarked completeness gain), then mono-depth fill with Apache/MIT weights (DAv2-Small, DA3 Apache models, MoGe-2) or Prior Depth Anything, then gsplat 2DGS; avoid MVSAnywhere, MASt3R, official 2DGS/PGSR/GOF/SuGaR, Neuralangelo/NeuS2, Depth Pro weights, DAv2 Base/Large and unlicensed PatchMatch repos for sold results.

### Inferences

  - Prior Depth Anything: Apache / Apache-tagged (backbone provenance to clarify); plausible; plausible good fit ("precise but incomplete" + mono); 1 day.

  - MapAnything-apache / DA3-Base with known poses: Apache / Apache; plausible with minibatch 1; coarse consistent depth prior; 1 day.

- For a plaster wall bounded by textured edges, the cheapest geometrically honest fill may be an explicit plane (or low-order surface) fitted to the wall's existing SfM points and PatchMatch border depths, written into the empty depth pixels of that wall segment - which is what ACMP/APD do internally with triangulated/deformed supports. The existing project tools that sweep depth around a fitted face (`kanten_tiefe_sweep_flaeche.py`, `tiefe_lokal.py`) already follow this idea; the external methods are mainly worth it if they deliver the same without per-wall setup.

### Gaps
- None of the candidates has been measured on this machine or on the project's data (internet + phone + video mix); every "8 GB plausible" needs a smoke test at 1600 px before a long run.
- Whether APD-MVS/ACMMP tolerate strongly mixed exposures of internet photos is unknown; a view-selection pre-filter (same-session images per reference) may be necessary.
